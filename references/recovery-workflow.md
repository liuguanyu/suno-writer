# 中断与未知提交恢复

在任务中断、超时、进程退出、部分专辑失败，或点击 Create 后未获得可靠结果时读取。恢复的首要目标是避免重复消耗 credits。

## 状态分类

1. **已知 batch/clip ID**：可恢复轮询、WAV 转换或下载，不需要再次 Create。
2. **尚未点击 Create**：不存在提交，可在重新 doctor 和重新确认后开始。
3. **已点击 Create，但没有可靠响应或结果**：标记 `unknown_submission_state`，不能推断成功或失败。
4. **专辑部分完成**：只以 album manifest 中逐曲状态为准，首个失败/未知曲目之后不得自动继续。

不要仅凭进程退出码、响应超时、页面仍显示表单或用户未看到新歌，就断言没有消耗 credits。

## 已知批次恢复

从已有 manifest 读取 batch 目录、batch ID、clip ID 与下载状态。只有项目已提供不通过命令行暴露认证信息的安全会话通道时，才运行：

```bash
pnpm resume <batch-dir>
```

当前实现若仍要求 `--bearer-token`、`--browser-token` 或 `--device-id`，应报告恢复能力缺口并停止，不得由 Agent 抽取或传递这些秘密。恢复命令只允许继续查询、转换和下载，不创建新批次。不得根据标题、时间戳或 URL 重新拼接 ID；不得把另一个批次的 ID 写入当前 manifest。

## 未知状态处理

遇到 `unknown_submission_state`：

1. 立即停止自动重试和剩余专辑提交。
2. 保留现有 manifest、输出目录和可核验证据，不覆盖为 pending 或 failed。
3. 使用项目已提供的确定性核对能力检查 Suno 结果；若当前 CLI 尚无核对命令，明确说明能力缺失，不要伪造 `inspect-submission` 命令，也不要由模型临时猜测私有接口。
4. 核对时优先依赖稳定 ID；标题、创建时间和 UI 可作为证据，但在不能唯一对应时仍保持未知。
5. 只有核对证明未创建，且重新运行 doctor 得到 `safeToSubmit=true`，并由用户再次明确授权 credits 后，才允许重试。
6. 若核对证明已创建，将实际 batch/clip ID 持久化后转为已知批次恢复，不能再次 Create。

## 专辑恢复

- 逐曲读取 album manifest，不从源 Markdown 重新推导已经提交的 batch ID。
- 已完成曲目不重复提交。
- 有已知 ID 的未完成曲目先恢复至终态。
- 存在未知曲目时停在该曲目，不自动从下一首继续。
- 要继续尚未提交的曲目，必须先消除所有更早曲目的未知状态，再重新 doctor，并让用户明确确认剩余提交数量。

## 向用户报告

报告应区分“确认已创建”“确认未创建”“状态未知”，列出对应 manifest/曲目和下一步。没有证据时不要声称 credits 为 0，也不要用安慰性措辞掩盖未知状态。
