# 单曲创作工作流

仅在创作、修改或校验单曲时读取。若要提交，继续读取 `doctor-workflow.md` 与 `submission-workflow.md`。

## 职责边界

- 模型负责理解需求、命名、歌词、Style 和审阅修改。
- TypeScript CLI 负责解析与确定性校验。
- 默认只生成 Markdown 草稿，不提交到 Suno。

## 流程

1. 收集必要需求：主题、语言、曲风、情绪、演唱方式、结构，以及用户明确提出的乐器或制作偏好。缺失项可给出合理创作选择，但不要捏造用户硬性要求。
2. 按 `output-contract.md` 生成单曲 Markdown。
3. 技术标签遵循 `suno-tags.md`。若用户指定流派、唱法或特殊配器，先读取 `styles/index.md`，再只读取命中的专题文件。默认生成“结构清晰、细节适量”的技术导演稿：使用标准 section token 锚定结构，只为主要段落追加 1–3 个最高优先级的人声、编配/律动或动态变化。不要只写保守的 `[Verse]`/`[Chorus]`，也不要把所有 Style 细节塞进超长标签。
4. 设计一条可听见的发展弧线：重复副歌体现一项明确的编配或和声增长，Bridge 形成核心对比，Final Chorus 或结尾给出高潮/收束；器乐独奏优先标注乐器与性格。小节数和逐句角色 cue 是概率性控制，不得表述为精确保证。
5. Style 使用英文，尽量覆盖流派、情绪、速度、调式、乐器、人声、动态和空间/混音，但不堆叠冲突描述。标签应细化各段执行，且与 Style 的全曲方向一致。
6. `不含技术词的歌词` 必须从带标签歌词中移除制作标签和行首角色 cue 后得到；实际演唱的中文括号回声、拖音和回应句应保留。它只用于审阅，不能提交到 Suno。
7. 非中文歌曲在四个固定部分后补充 `中文翻译`。
8. 将草稿交给用户审阅；修改时只调整用户指出或确有必要的部分，不无故重写整首。
9. 运行确定性校验：

```bash
pnpm validate <song.md> [--mode=strict|minimal]
```

10. 修复校验指出的创作或格式问题，并重新校验。未经提交阶段的明确确认，到此结束。

## 提交前检查

- `歌词`、`Style`、`歌名` 与纯歌词部分齐全且顺序正确。
- 页面字段长度符合 `output-contract.md`。
- 主要段落使用标准结构锚点和少量、不矛盾的局部控制；重复段落体现发展而非机械复制。
- 严格小节数、精确进入点、固定声部身份不依赖一次生成；如为验收条件，应规划 Studio/DAW 后期。
- 纯歌词不包含制作标签或角色 cue，但保留实际演唱的回声与回应。
- 只将歌词、Style、歌名三个字段交给 Suno。
- 用户提出“直接生成”也不能跳过校验、doctor 和 credits 确认。
